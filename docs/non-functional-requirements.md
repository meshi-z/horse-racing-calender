# 非機能要件仕様書 (Non-Functional Requirements Specification: NFR)

本ドキュメントは、`horse-racing-calendar` における非機能要件、性能目標（SLO / KPI）、計測条件、および運用ガイドラインを定義する正本（Single Source of Truth）です。  
`.agents/rules/30-performance.md` に基づき、すべての開発者およびAIエージェントは本仕様書を準拠基準として設計・実装・検証を行います。

---

## 1. 背景と目的

現在、開催国の拡充（日・英・仏・米・香・愛）に加え、将来的な対象年度の追加（2027年以降の番組追加）や年末年始に向けた新国・地域（UAE、サウジアラビア、オーストラリア等）の追加により、管理対象レース数は数千件規模へと拡大することが確実となっています。

全レースデータやDOMノードを無制限にクライアント上に展開・レンダリングすると、以下の重大な課題が発生します：
1. **初期データ転送量の肥大化**: 通信速度が制限された環境やモバイル回線での表示遅延。
2. **DOMツリーの過剰展開による描画劣化**: スクロール追従のカクつき（ジャンク）、フィルタ切り替え時のメインスレッド占有、INP（Interaction to Next Paint）悪化。
3. **メモリ枯渇（OOM）**: 低スペックなモバイル端末におけるブラウザタブの強制クラッシュ。

本仕様書では、レース件数が数千件規模に達してもミリ秒単位の快適な操作性を担保するため、定量的かつ測定可能な性能指標および設計基準を定めます。

---

## 2. 性能指標・目標値 (SLO / KPI)

### 2.1 操作応答性 (Interaction to Next Paint: INP)

ユーザーの入力（タップ、クリック、キー入力）から次フレームの描画更新が完了するまでの時間。

| 指標 / 操作項目 | 許容上限値 | 推奨目標値 | 備考 / 計測条件 |
| :--- | :--- | :--- | :--- |
| **フィルター切り替え応答時間** | **100ms 未満** | **16ms 〜 50ms** | 主催者・グレード・国コード・競馬場・馬場・距離等のトグル操作。60fpsの描画滑らかさを維持すること。 |
| **表示モード切り替え** | **150ms 未満** | **50ms 〜 100ms** | タイムライン ⇄ 月間カレンダーのタブ切り替え。 |
| **レース詳細ダイアログ表示遅延** | **100ms 未満** | **30ms 〜 60ms** | レースカードクリックからモーダル展開完了まで。 |
| **日付ジャンプ / 自動スクロール** | **100ms 未満** | **16ms 〜 50ms** | 「今日へ戻る」ボタン等のスムーズスクロール開始までの遅延。 |

### 2.2 クライアント描画負荷 (DOMノード数 & メモリ消費)

DOMノード数およびJavaScriptヒープメモリの消費を抑制し、描画パイプライン（Recalculate Style / Layout）の負荷を最小化する。

| 項目 | 許容上限値 | 推奨目標値 | 対策・設計基準 |
| :--- | :--- | :--- | :--- |
| **同時展開DOMノード数** | **常時 1,500 ノード以下** | **800 〜 1,000 ノード** | 全登録レース数が数千件に達した場合でも、画面表示領域＋前後バッファのみを描画する仮想スクロール（Virtualization）または遅延描画（Windowing）の導入。 |
| **メモリ使用量 (JS Heap)** | **50 MB 以下** (モバイル基準) | **20 〜 30 MB** | 不要なオブジェクト生成の抑制、ストアの不変性（Immutability）維持、デリファレンスによるGCの効率化。 |
| **長時間操作時のメモリリーク** | **0 バイト** | **完全解放** | リスナー解除、タイマー・インターバルの適切なクリーンアップ。 |

### 2.3 ロード性能 (Core Web Vitals & ネットワーク転送)

モバイル環境および外出先（競馬場等）の不安定なネットワーク環境を想定した初期表示性能。

| 指標 | 許容上限値 | 基準環境 | 備考 |
| :--- | :--- | :--- | :--- |
| **LCP (Largest Contentful Paint)** | **2.5秒 未満** | モバイル (Fast 3G / Slow 4G 相当) | 初期レースカード・タイムラインの主要コンテンツ描画完了まで。 |
| **INP (Interaction to Next Paint)** | **200ms 未満** | モバイル (CPU 4x Slowdown) | Google Core Web Vitals "Good" 水準を死守。 |
| **CLS (Cumulative Layout Shift)** | **0.1 未満** | 全環境 | レース一覧読み込み中・読み込み後でレイアウトシフト（ガタつき）を発生させない。スケルトン表示領域の事前確保。 |
| **初期データ転送量 (Data Transfer)** | **gzip 100KB 未満** (生JSON 1MB 未満) | 初期ロード時 | 登録レース数が拡大しても、年度別Sharding（`races-2026.json` 等）またはメタデータ分離により初期ペイロードを制限。 |

### 2.4 バンドルサイズ目標 & コード分割基準 (Bundle Size & Code Splitting)

Vite / Rollup によるプロダクションビルド成果物のサイズ制限。

| チャンク種別 | 許容上限 (生ファイル) | 許容上限 (gzip) | 備考 |
| :--- | :--- | :--- | :--- |
| **メインJSチャンク (`index.js`)** | **350 KB 未満** | **100 KB 未満** | アプリケーションの基底バンドル。 |
| **総JS転送量 (初期表示)** | **500 KB 未満** | **150 KB 未満** | 初期表示に必須なチャンクの総和。 |
| **メインCSSチャンク (`index.css`)** | **60 KB 未満** | **15 KB 未満** | Tailwind CSS の未使用スタイルパージ徹底。 |

#### コード分割 (Code Splitting) の適用基準:
- **カレンダービュー (`CalendarView`)**: モバイル表示では初期不要のため、タブ選択時または画面幅 `>= 768px` でのみ動的インポート（`React.lazy`）を検討。
- **各種ヘルプ・情報モーダル**: ユーザーの明示的なトリガー操作（クリック）で初めて表示されるコンポーネントは動的読み込み対象とする。
- **外部大型ライブラリの追加禁止**: 日付計算ライブラリ（moment等）や巨大アイコンパック全体の一括インポートを禁止し、必要最小限の軽量関数・個別インポートに限定する。

## 3. パフォーマンス計測手法 & 運用ガイドライン

### 3.1 計測環境の標準プロファイル

性能測定を行う際は、開発マシンのハイスペック環境ではなく、以下のスロットリング環境を基準とする。

- **CPU スロットリング**: **4x CPU Slowdown**（一般的なミドルレンジスマートフォン相当）
- **ネットワーク スロットリング**: **Fast 3G** (Down: 1.6 Mbps, Up: 750 kbps, RTT: 150ms) または **Slow 4G**

### 3.2 計測ツールと実行手順

#### 1. Chrome DevTools Performance パネル (INP / メインスレッド計測)
1. Chrome DevTools を開き、Performance パネルを選択。
2. ギアアイコン（Capture settings）から `CPU: 4x slowdown` を設定。
3. 録画を開始し、以下の操作を実行：
   - フィルターを複数回連続して切り替える（主催者、グレード等）。
   - タイムライン ⇄ カレンダーを切り替える。
   - レースカードをクリックして詳細ダイアログを開閉する。
4. 録画を停止し、**Interactions** セクションの INP 値、および **Main** スレッドの `Long Task`（50ms超のタスク）の有無を確認する。

#### 2. Lighthouse CLI による Core Web Vitals 計測
プロダクションビルド・ローカルプレビュー環境に対して Lighthouse を実行する。

```bash
# プロダクションビルドのプレビュー起動
npm run build
npm run preview

# Lighthouse 実行 (別ターミナル)
npx lighthouse http://localhost:4173 --preset=mobile --throttling-method=devtools --output=html --output-path=./scratch/lighthouse-report.html
```

- **合格基準**:
  - Performance スコア: **90点以上**
  - LCP: 2.5秒 未満
  - TBT (Total Blocking Time): 200ms 未満
  - CLS: 0.1 未満

#### 3. バンドルサイズの検査
プロダクションビルド実行時の Vite 出力ログを確認する。

```bash
npm run build
```

出力される `dist/assets/index-[hash].js` のファイルサイズが、本仕様書「2.4 バンドルサイズ目標」の基準（生 350KB 未満 / gzip 100KB 未満）内に収まっていることを確認する。

## 4. 将来拡張における受入基準 (Acceptance Criteria)

今後予定されている大規模パフォーマンス改善タスクの実装時は、本仕様書を以下の通り受入基準とする：

1. **タイムライン仮想スクロール（Virtualization）タスク**:
   - 登録レース数が 2,000 件を超過した状態でも、DOMノード数が **1,500 ノード以下** に維持されること。
   - スクロール中の FPS が 55fps 以上を維持すること。
2. **データ Sharding（年度別分割 / オンデマンド読み込み）タスク**:
   - 初期ロードで取得するレースデータ JSON の転送量が **gzip 100KB 未満** であること。
   - 別年度への切り替え時にキャッシュを活用し、2回目以降の表示が 100ms 未満で完了すること。
